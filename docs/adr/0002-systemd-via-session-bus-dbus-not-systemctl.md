# Talk to systemd via the user session bus D-Bus API, not systemctl

ussd must operate systemd user units and observe out-of-band state changes continuously. `systemctl --user` offers no observation channel at all (every call is a fresh process on a private socket), a text/exit-code error protocol, and a 5.3–6.4 ms floor per call — while a persistent D-Bus connection round-trips in ~1–2 ms and is the only path to state-change signals: the user manager emits session-bus signals only while ≥1 client has called `Subscribe()` (verified against the man page and v262 source). Decision: uss and ussd talk to `org.freedesktop.systemd1` directly on the user session bus using pure-Rust `zbus` 5 + `zbus_systemd` (systemd1 feature) — no FFI (crate policy), no systemctl shelling. The watchdog calls `Subscribe()` on connect and after every reconnect, watches `PropertiesChanged` on member unit objects and `JobRemoved` for operation outcomes, and re-syncs state on start/reconnect because signals are not replayed. Measured out-of-band-start detection: ~5–6 ms.

**Considered options**: `systemctl --user` shelling (rejected — no signals, per-call process cost, no structured errors); `sd-bus`/libsystemd via `libsystemd-sys` (rejected — FFI would need explicit per-crate approval, and the binding is stagnant); `systemd-dbus` (dead since 2015); `systemd-zbus` (repo dead since 2022); `dbus-rs` (active but general-purpose, not systemd-shaped).

**Consequences**: ussd's correctness hinges on the `Subscribe()` refcount gate — re-subscribe and re-sync on every reconnect is a hard requirement, not a nicety; bootstrap must fail with an explicit error when the user manager is absent (no session, no linger); the first-use auto-install flow (write unit file → `Reload()` → `EnableUnitFiles` → `StartUnit` + wait `JobRemoved(result="done")`) is D-Bus-only. Evidence: `docs/research/2026-10-02-systemd-interface.md` on branch `research/systemd-interface` (measured latency, source-verified signal gate, live probe runs).
